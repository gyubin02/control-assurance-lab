# 2026-07-29 범위 재설정

이 문서는 멋있게 보이기 위한 소개글이 아니다. 첫 설계 회의에서 확인한 사실과 아직 결정하지 않은 것을 구분해 두는 작업 노트다.

## 출발점

이전에 만든 CVE-2026-59891 control lab은 취약 버전과 수정 버전을 재현하는 데는 쓸모가 있었다. 하지만 그것을 “보안 통제 관리 프로젝트”라고 부르기에는 부족했다.

부족했던 이유는 구체적이다.

- 실제로는 패키지 버전과 몇 가지 설정을 검사하는 도구에 가까웠다.
- 위험, 통제, 시험, 증거, 개선, 재시험이 하나의 운영 흐름으로 이어지지 않았다.
- 통제가 왜 효과가 있었는지와 단지 마지막 공격이 실패했다는 사실을 구분하지 못했다.
- 기존 HackerOne 재현 자료에서 새로 배울 실무 지식이 충분하지 않았다.
- 먼저 그럴듯한 문장을 만들고 기능의 의미를 나중에 붙이는 순서였다.

기존 저장소는 버리지 않는다. 나중에 공급망 인증 경계 시나리오 하나로 사용한다. 다만 새 프로젝트의 중심은 아니다.

## 선행조사에서 바로 버린 생각

“공격을 실행하고 탐지 여부를 대시보드에 보여주는 오픈소스 BAS”는 새롭지 않다. OpenAEV가 이미 시나리오 실행, 예방·탐지·대응 기대값, 보안 제품의 경보 수집, 재시험을 제공한다. CALDERA, Atomic Red Team, Stratus Red Team도 공격 행동 실행과 원시 기록을 각자의 범위에서 잘한다.

“자동 검사 결과를 통제와 규정에 연결해서 감사 증적을 만든다”도 새롭지 않다. OSCAL, Compliance Trestle, Compliance-to-Policy, Prowler, Powerpipe가 이미 많은 부분을 다룬다.

“주장-논증-증거 그래프를 만든다”도 보증 사례 분야에서 오래 연구되었다.

따라서 위 기능을 한 화면에 합치는 것만으로는 큰 프로젝트일 수는 있어도 좋은 연구 질문은 아니다.

## 지금 남은 질문

최종 공격이 막혔을 때 무엇이 막았는지를 어떻게 입증할까?

예를 들어 애플리케이션의 권한 검사가 고장 났지만 WAF가 우연히 요청을 막았다면:

- “고객 정보 유출은 막혔다”는 경로 수준 결과는 맞다.
- “애플리케이션 권한 통제가 정상이다”는 주장은 틀렸다.

두 결과를 하나의 초록색 점수로 합치면 고장 난 통제가 가려진다.

반대로 권한 통제를 켠 뒤 공격이 실패했다고 해서 바로 그 통제 덕분이라고 말할 수도 없다. 서버가 죽었거나, 테스트 데이터가 달라졌거나, 다른 방화벽 규칙이 바뀌었을 수 있다.

그래서 다음 조건을 만족하는 대조실험이 필요하다.

1. 비교 대상 사이에서 바꾼 것은 목표 통제 하나여야 한다.
2. 실제로 그 통제가 바뀌었는지 별도의 관측으로 확인해야 한다.
3. 공격 입력과 나머지 환경이 같았는지 지문과 실행 기록으로 확인해야 한다.
4. 공격 동작은 달라지고 정상 동작은 보존되어야 한다.
5. 통제의 실행 지점에서 어떤 결정이 났는지 관측해야 한다.
6. 다른 통제가 최종 피해를 막더라도 목표 통제의 실패는 실패로 남겨야 한다.

이 기록 묶음을 현재는 `interventional witness`라고 부른다. 이름은 확정하지 않았다. “인과 증명”이라는 표현은 실험 조건과 외적 타당성이 충분하지 않으면 과장이다.

## 사람의 기록으로 남기기 위한 규칙

- 실패한 실험을 성공한 것처럼 정리해서 지우지 않는다.
- 결정하지 않은 것을 이미 결정한 것처럼 쓰지 않는다.
- 원시 로그와 최종 판정을 같이 보존한다.
- 도입한 기술마다 “이 기능을 실제 시나리오나 벤치마크가 사용하는가?”를 확인한다.
- 파일 수, 서비스 수, 프레임워크 수를 성과처럼 세지 않는다.
- 사용자가 설명하지 못하는 문장은 포트폴리오 문서에 넣지 않는다.
- 공개 문서에서는 AI 도움을 숨기기 위한 연기를 하지 않는다. 대신 사용자가 직접 검증하고 수정한 판단의 범위를 분명히 한다.

## 아직 결정하지 않은 것

- 공개 이름
- 구현 언어와 UI 스택
- 첫 번째 금융 시나리오의 정확한 업무 흐름
- 제조/R&D 시나리오를 첫 릴리스에 함께 넣을지 여부
- 증거 서명 방식
- 실험 반복 횟수와 통계 판정 기준
- OSCAL 내보내기의 지원 범위

이 항목은 코드를 먼저 만든 뒤 합리화하지 않고, 작은 비교 실험이나 근거를 남긴 뒤 결정한다.
